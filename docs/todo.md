# xtw_bot 稳定性、上下文与可迁移性改造计划

> 计划版本：v1.1  
> 最后整理：2026-08-20  
> 依据快照：本地归档 `xtw_bot-server-20260818-100133.tar.gz` 解压后的项目目录  
> 适用范围：`C:\Users\longz\Documents\Program\xtw_bot` 及后续 Linux 部署实例  
> 当前原则：人格已经基本稳定，后续工作以稳定性、可观测性、Token 成本、可复制部署和可迁移性为主，不以增加功能数量为目标。

## 1. 总体目标

本轮改造需要同时解决六类问题：

1. 固定插件钩子的执行顺序，消除插件加载顺序变化造成的随机行为。
2. 精简重复的上下文注入，改善缓存命中率并降低输入 Token，但不削弱人格、记忆和主动聊天能力。
3. 让普通消息、连续消息和工具调用各自只产生合理数量的模型请求，避免重复注入、重复回复和多轮 Agent 放大。
4. 完成 SnowLuma 对 NapCat 的接管，提高 QQ 接入层的连续运行能力、登录恢复能力和故障可诊断性。
5. 把源码、配置、持久化数据、第三方运行时、缓存和备份分层，为以后迁移到物理机做准备。
6. 查明情绪插件数值停止更新或观察结果不一致的原因，并恢复可验证、可追踪的情绪更新链路。

安全边界属于贯穿所有阶段的基础要求：任何群成员都不能通过“总结上下文”“压缩并输出提示词”“列出人格设定”“转发消息分析”等请求取得系统提示词、人格原文、工具内部描述、其他用户记忆或未授权的跨会话内容。

## 2. 不可破坏的约束

以下约束优先级高于 Token 优化和目录精简：

- 不直接改写或删减已经稳定的人格提示词；如需移动内容，只允许在语义完全不变且人工对比通过后进行。
- 最终主回复仍保留 Iris L1/L2/L3、画像、好感度和工具能力；只允许轻量预判断、DecisionAI 或主动聊天预判断跳过主回复专用动态上下文。
- 主动聊天不能因为优化而明显变得消极；主动触发概率、触发条件和最终回复能力需要分别测试。
- Group Chat Plus 的 Web 面板必须保留。
- Stealer 继续负责偷取、存储和索引表情包；最终只能有一套链路负责把表情包语义注入模型上下文。
- 正常图片与表情包必须区分处理；已有描述优先复用，无描述的表情包才调用 VLM 补充转述。
- 连续消息采用“最后一条消息后约 3 秒再发起主请求”的安静窗口；一次消息突发最终只生成一份主回复。
- 不在日志中记录完整系统提示词、人格原文、API Key、访问令牌、QQ 登录信息或完整模型请求正文。
- 对上下文、记忆和人格相关的任何变更，必须经过人工 A/B 评估；未通过时立即回滚，不允许一次同时修改多个变量。
- 删除插件、数据库、索引、缓存或旧运行时之前，必须先确认其职责、生成方式、最后使用时间和回滚来源。
- NapCat 已弃用：不得重新加入默认启动、故障切换或新面板；只允许在确认 SnowLuma 稳定后归档其旧数据和清理残留。

### 3.1 当前安装插件

```text
astrbot_plugin_stealer

```

`PROJECT_STRUCTURE.md` 是历史快照，插件清单已经过期；实施时以 `astrobot/data/plugins/` 的真实目录和 `PROJECT_DOCUMENTATION.md` 为准，并同步更新文档。

### 3.2 当前 LLM 请求钩子顺序

已确认 AstrBot 按 priority 数值从高到低执行。当前主要顺序如下：

| 优先级 | 插件或职责 | 当前风险 |
|---:|---|---|
| `+1000` | AstrNa 生命周期处理 | 必须确认它是否修改请求、取消请求或只做状态管理 |
| `+999` | AntiPromptInjector 前置检查 | 与最终安全检查属于同一插件的两段式流程 |
| `+100` | Debounce、Recall Cancel | 两者同优先级，谁先执行仍依赖注册顺序 |
| `+10` | Affection | 注入动态情绪，同时异步触发数值调整 |
| `+1` | Input State by NapCat（遗留插件） | 输入状态提示；需确认 SnowLuma 下是否仍兼容，否则移除或替换 |
| `0` | Iris、Shared Context、Stealer、QZone Tools、Tool Use Cleaner 等 | 同级最多，是当前最主要的不确定顺序区 |
| `-1` | Group Chat Plus | 恢复、合并 prompt、contexts、工具和运行时提示 |
| `-10` | Context Aware | 在靠后位置追加群聊场景和图片信息 |
| `-1000` | AntiPromptInjector 最终检查 | 应作为发送给 Provider 前的最后安全门之一 |

主要问题不只是 priority=0：`Debounce` 与 `Recall Cancel` 也同为 `+100`。此外，工具调用进入下一轮 Agent 时会再次执行整条 `on_llm_request` 链路，因此顺序正确仍不足够，还必须保证所有动态注入幂等。

### 3.3 上下文职责重叠

当前可能同时参与同一请求的上下文来源包括：

- AstrBot 内置会话历史；
- Group Chat Plus 最近群聊历史和运行时提示；
- Context Aware 群聊场景、图片和对话流分析；
- Iris L1/L2/L3、画像、好感度与工具提示；
- Shared Context 跨会话消息；
- Affection 动态情绪；
- Stealer 表情包语义；
- QZone Tools 和其他工具说明；
- AntiPromptInjector 的安全检查或安全提示。

重复内容可能同时出现在 `system_prompt`、`contexts`、`prompt` 和 `extra_user_content_parts`。Group Chat Plus 又会在后段恢复或合并请求字段，因此仅查看某个插件执行后的请求不能代表最终发给模型的内容。

### 3.4 情绪插件的初步观察

本地归档显示：

- `astrobot_plugin_affection_config.json` 中 `unconscious_llm.provider_id` 为空。
- 普通互动分析会回退到当前会话模型；空闲分析会回退到字面值 `default`。两条路径可能使用不同 Provider，也可能有一条失败。
- 真实机器人目录 `plugin_data/astrbot_plugin_affection/<BOT_ID>/` 的数据文件更新到 2026-08-18 10:02 左右。
- `plugin_data/astrbot_plugin_affection/default_bot/` 的文件更旧。

因此“情绪插件完全没有生效”目前不能直接成立。更可能的情况包括：查看了错误的 bot 数据目录、后台 LLM 调用失败、事件被重复或未触发、Provider 回退不一致、异步任务异常只写日志但没有明显告警，或情绪变化幅度太小而被误认为未更新。

### 3.5 SnowLuma 接管与目录现状

- NapCat 已弃用，不再作为现役服务、回退服务或迁移目标；其 Docker/AppImage、Xvfb 和登录数据只作为待确认的历史资产处理。
- SnowLuma 是唯一现役 QQ 接入层。实施时需要补录其真实安装路径、部署方式、镜像/版本、配置格式、端口映射和持久化目录，不能把旧 NapCat 假设直接套用过去。
- SnowLuma 需要固定到经过验证的版本或镜像 digest；使用漂移标签会削弱可复现性。
- 项目根目录同时包含源码、`astrobot`/`astrobot2`、`.runtime`、NapCat、数据库、QQ 数据、日志、缓存、浏览器运行时、`node_modules` 和多代备份。
- 当前目录不是 Git 仓库，定制插件源码和第三方原始文件之间也没有统一的变更清单。

## 5. 阶段 0：建立基线、观测和回归门禁

### 5.1 目标

在改代码前回答三个问题：当前每条消息实际触发几次模型请求、每个上下文来源贡献多少内容、哪些能力是用户认为“人格正确”的必要部分。

### 5.2 实施任务

- [ ] 从现有完整归档复制一份只读基线，记录归档文件名、大小和 SHA256。
- [ ] 生成运行版本清单：AstrBot、Python、SnowLuma、Docker 镜像 ID、Node、各插件版本、模型 Provider ID 和 Embedding Provider ID；NapCat 仅记录历史归档版本。
- [ ] 对所有定制插件源码和配置生成 SHA256 清单；配置清单必须脱敏，不记录密钥和令牌。
- [ ] 建立请求追踪 ID，至少记录：消息 ID、会话 ID 哈希、请求轮次、是否工具轮、Hook 名称、执行前后字段长度、工具数量、图片数量和内容哈希。
- [ ] 日志只记录长度、数量、哈希和来源标签，不记录完整 prompt、contexts、人格或用户记忆原文。
- [ ] 在 Cost Control 面板记录至少 24 小时基线：输入命中缓存、输入未命中缓存、输出 Token、请求数、平均延迟和 P95 延迟。
- [ ] 建立人工回归语料，不直接使用真实敏感聊天内容；至少覆盖以下场景：
  - 私聊单条普通消息；
  - 私聊连续 3～5 条消息，最后一条后等待 3 秒；
  - 群聊 @ 机器人；
  - 群聊未 @ 但应主动参与；
  - 正常图片；
  - 有描述和无描述的表情包；
  - 合并转发消息；
  - 一次无工具请求；
  - 一次单工具请求；
  - 一次多轮工具请求；
  - 安全注入与人格套取请求。
- [ ] 保存 20～30 个代表性回答作为人格基线，由人工标注：语气、关系感、记忆准确性、群聊自然度、主动性、分句方式和安全性。

### 5.3 基线指标

每次后续改动至少对比以下指标：

- 无工具普通消息的主模型请求数应为 1。
- 连续消息突发在安静窗口结束后应合并为 1 次主请求和 1 份最终回复。
- 工具任务允许产生必要的 Agent 轮次，但每轮必须有明确原因，不能因重复 Hook 注入产生额外请求。
- 同一动态上下文块在单个 ProviderRequest 中只能出现一次。
- 缓存命中 Token 比例、未命中 Token、总延迟和错误率均有前后对照。
- 人格人工评估不得出现明显下降；任何安全泄漏属于直接失败。

### 5.4 阶段完成标准

- 能从一条 QQ 消息追踪到所有模型请求和最终回复。
- 能区分“合法工具轮次”和“意外重复请求”。
- 能看到各插件注入的大小和哈希，但日志中看不到原文。
- 基线测试可以重复执行，结果格式固定。

## 6. 阶段 1：分配显式 Hook 顺序

### 6.1 目标

消除同优先级依赖注册顺序的问题，同时维持 Group Chat Plus 的请求收束能力和 AntiPromptInjector 的前后两段安全检查。

### 6.2 先建立职责顺序

建议先按语义确定顺序，再分配数值，不要直接为每个插件随意加减 1：

1. 生命周期、取消与安全前置检查；
2. 召回取消与消息防抖；
3. 平台输入状态；
4. 动态情绪；
5. Iris 记忆和画像；
6. Shared Context 跨会话内容；
7. Stealer 表情包语义；
8. QZone 等工具上下文；
9. 工具清理与工具清单规范化；
10. Group Chat Plus 请求收束；
11. Context Aware 最终群聊场景；
12. AntiPromptInjector 最终安全检查。

建议为不同职责预留 priority 区间，例如：

| 区间 | 职责 |
|---:|---|
| `1000～900` | 生命周期、取消、安全前置和防抖 |
| `199～100` | 平台状态和全局运行状态 |
| `99～20` | 情绪、记忆、共享上下文、表情包和工具上下文 |
| `0～-100` | Group Chat Plus 收束与最终场景构造 |
| `-900～-1000` | 最终安全检查和发送前门禁 |

具体数值必须在确认 AstrNa、Recall Cancel 和 AntiPromptInjector 的实际语义后落定。最终同一生命周期内不应再有两个修改请求对象的 Hook 使用相同 priority。

### 6.3 实施任务

- [ ] 输出 `docs/HOOK_ORDER.md`，列出插件、函数、生命周期、当前 priority、是否修改请求、是否可阻断、是否会异步发起模型请求。
- [ ] 逐一确认 AstrNa `+1000` 的职责，避免它和 Recall Cancel、Debounce 重复取消同一请求。
- [ ] 明确 Recall Cancel 先判断已撤回/过期事件，还是 Debounce 先判断消息突发；为二者分配不同 priority。
- [ ] 为 Iris、Shared Context、Stealer、QZone Tools 和 Tool Use Cleaner 分配不同 priority。
- [ ] 保持 Group Chat Plus 晚于需要被它观察和合并的插件。
- [ ] 保持 Context Aware 晚于 Group Chat Plus，或在验证后将其场景块纳入 Group Chat Plus 的正式合并协议；二者只能选择一种稳定契约。
- [ ] 保持 AntiPromptInjector 最终检查位于所有 prompt/context/tool 修改之后。
- [ ] 增加自动化顺序测试：随机改变插件发现/注册顺序时，实际 Hook 执行序列仍保持一致。
- [ ] 在插件升级后自动检查 priority 漂移和新增默认 priority=0 Hook。

### 6.4 验收标准

- 启动 10 次或模拟 10 次不同注册顺序，Hook 顺序完全一致。
- Debounce 与 Recall Cancel 不再同优先级。
- 所有会修改 `ProviderRequest` 的主要 Hook 都有明确、文档化的 priority。
- 普通消息、图片、转发消息和工具轮次均通过阶段 0 回归测试。

### 6.5 回滚

每个插件修改前保存原文件和配置；priority 调整以单插件为单位提交。出现人格丢失、记忆不注入、工具消失或安全检查绕过时，先回滚最近一个 priority 变更，不同时回滚整组插件。

## 7. 阶段 2：修复并验证情绪插件

### 7.1 目标

确认情绪链路是“未触发、调用失败、写错目录、重复更新、变化太小或查看错误”，然后恢复稳定更新。不能通过直接重置所有数值来掩盖根因。

### 7.2 诊断步骤

- [ ] 确认插件加载日志、`on_waiting_llm_request` 和 `on_llm_request(priority=10)` 均成功注册。
- [ ] 在同一条测试消息上记录 bot ID、用户 ID 哈希、消息 ID、任务启动、Provider ID、LLM 返回解析结果和数据写入结果。
- [ ] 确认真实 bot ID 始终为 `<BOT_ID>`，避免部分事件写入 `default_bot`。
- [ ] 对比 `<BOT_ID>/user_data.json` 与 `default_bot/user_data.json`，确认 Web 面板或命令读取的是哪一份数据。
- [ ] 将 `unconscious_llm.provider_id` 从空值改为显式的 DSV4F Provider ID；修改前先确认该 ID 在当前 AstrBot 配置中真实存在。
- [ ] 统一普通互动分析与 idle 分析的 Provider 选择逻辑，禁止一条回退到当前会话模型、另一条回退到字符串 `default`。
- [ ] 为 LLM 空输出、非 JSON、超时、Provider 不存在和 API 400 分别记录错误类型和有限重试结果。
- [ ] 为同一消息 ID 增加情绪更新幂等锁，避免消息重复或 Agent 多轮造成多次好感度调整。
- [ ] 保存后台任务句柄，并在插件卸载或重载时正常取消；捕获未处理的异步异常。
- [ ] 检查衰减任务是否每个 bot 只启动一份，避免插件重载后产生多个 DecayManager。

### 7.3 功能验收

- 连续发送 5 条测试消息，每条只产生一次情绪分析记录。
- 第二条及以后消息能按规则更新数值；首条消息只初始化的行为需要在文档中说明。
- 数值写入 `<BOT_ID>/`，Web 面板和 `/mystatus` 读取同一份数据。
- 重启 AstrBot 后数据不丢失、不重置，衰减任务只有一份。
- DSV4F 异常时主回复仍可继续，但情绪任务产生可见告警，不静默失败。
- 人工确认情绪变化不会让人格表现突然失控，也不会在回复中暴露数值。

## 8. 阶段 3：精简上下文层并改善私聊记忆

### 8.1 目标

建立“一个信息只有一个权威来源”的上下文架构。精简指删除重复注入，不是删掉能力。最终主回复保留完整人格、长期记忆和工具；轻量预判断只获取完成判断所需的最小信息。

### 8.2 字段所有权

建议固定以下所有权：

| 请求字段 | 唯一主要职责 | 不应放入的内容 |
|---|---|---|
| `system_prompt` | 静态人格、固定安全边界、稳定工具规范 | 每轮变化的聊天历史、情绪数值、检索结果 |
| `contexts` | AstrBot 的规范化近期会话历史 | 画像全文、重复群聊历史、插件调试说明 |
| `prompt` | 当前用户消息和必要的当前轮结构 | 再复制一份完整会话历史或系统提示词 |
| `extra_user_content_parts` | Iris 检索、情绪、Shared Context、群聊场景等临时动态块 | 永久人格原文和无法去重的大段静态说明 |
| `tools` | 规范化且去重后的最终工具集合 | 同名不同 schema、重复别名或仅供预判断的无关工具 |

### 8.3 插件职责建议

- AstrBot 内置历史：作为近期对话的唯一权威历史。
- Group Chat Plus：保留 40 条群聊主上下文限制，负责群聊选择、主动聊天和请求收束，不再复制已经存在于 `contexts` 的同一历史。
- Context Aware：只提供“当前群聊场景、指代对象、回复目标和必要图片说明”，不再注入另一份原始聊天历史。
- Iris：L1 负责缓冲和转存，L2/L3/Profile 负责按需检索；检索结果通过临时块注入，并带来源 ID 和去重键。
- Shared Context：只注入跨会话确有必要的内容，不复制当前会话最近消息。
- Affection：每轮最多一个动态情绪块。
- Stealer：只在识别为表情包且缺少可用描述时提供 VLM 语义；正常图片交给主图片链路。
- Tool Use Cleaner：只做工具消息清理和格式规范化，不再次加入工具说明全文。

### 8.4 私聊上下文改造

- [ ] 分开设置群聊和私聊预算，不把群聊的 40 条限制直接套到私聊。
- [ ] 私聊近期历史以 Token 预算为主、消息条数为辅；先用基线数据确定合理范围，再选择初始值。
- [ ] 超出窗口的私聊内容先摘要或结构化后写入 Iris L2，不直接丢弃。
- [ ] 为 L2 写入设置明确触发点：窗口淘汰、会话结束、达到消息阈值或定时任务。
- [ ] 提高 L2/L3 检索积极性时，同时设置相关性阈值、最大条数和 Token 上限，避免“积极检索”变成“每轮塞满记忆”。
- [ ] 建立私聊记忆测试集：近期事实、跨天事实、关系变化、用户偏好和不应记住的临时内容。
- [ ] 检查画像、好感度和 L2 之间是否重复描述同一关系；保留权威版本，其他层只引用 ID 或摘要。

### 8.5 轻量预判断与最终主回复分流

- DecisionAI 和主动聊天预判断跳过 Iris L1/L2/L3、画像全文、好感度数值、完整工具清单和其他主回复专用动态上下文。
- 预判断只接收：最近少量群消息、是否被提及、当前时间、冷却状态、是否已有回复中的请求、主动聊天概率和必要安全标记。
- 预判断决定需要发言后，再为最终主回复构造完整上下文。
- 预判断变轻不能降低主动性；主动概率、冷却时间和触发特征独立于上下文精简进行调整。

### 8.6 单变量实施顺序

每完成一步都执行完整回归和人工评估：

1. 先只增加观测和来源标签，不改变内容。
2. 去掉完全相同的重复块。
3. 让 Context Aware 停止复制原始历史，只保留场景。
4. 让 Shared Context 排除当前会话已存在消息。
5. 统一表情包语义注入。
6. 调整 Iris 的检索预算与写入策略。
7. 最后再考虑停用某个插件的子功能。

### 8.7 人工评估门禁

每次变更使用同一组输入做盲测，至少评价：

- 人格是否仍像“小天文”；
- 是否记得正确的人和关系；
- 群聊里是否知道在和谁说话；
- 是否仍会适度主动参与；
- 图片和表情包理解是否自然；
- 回复是否按既有配置分句；
- 是否出现重复描述、记忆拼接痕迹或明显系统说明。

任何一项明显下降时不继续下一步，先回滚并定位具体上下文来源。

## 9. 阶段 4：精简请求收束层和工具调用

### 9.1 目标

保证每个请求轮次可识别、每个插件注入幂等、工具集合稳定，避免“发几条消息就调用几次模型”“一次 400 后提交两份请求”“工具循环反复附加整套上下文”等问题。

### 9.2 请求生命周期设计

每条原始消息或防抖后的消息突发生成一个稳定的 `request_id`，每次模型调用增加 `round_index`：

```text
消息突发
  → request_id
  → round 0：最终主回复首轮
  → round 1..N：必要的工具调用轮
  → final：只发送一份最终结果
```

需要区分：

- `source_message_ids`：防抖合并前的原始消息列表；
- `request_id`：一次用户意图；
- `round_index`：Agent 工具轮次；
- `final_response_sent`：是否已经向 QQ 发送最终回复；
- `injection_markers`：本轮已执行的动态注入集合。

### 9.3 实施任务

- [ ] Debounce 在最后一条消息后约 3 秒创建唯一的合并事件，旧定时器必须取消，旧请求不得继续调用 Provider。
- [ ] Recall Cancel 与 Debounce 共享或兼容同一请求状态，避免一个取消、另一个又重新创建请求。
- [ ] Group Chat Plus 不依赖脆弱的 `event.extra` 临时状态作为唯一数据源；清理前先把必要状态复制到请求级对象。
- [ ] 所有注入块包含稳定去重键，例如 `iris:l2:<memory_id>`、`context_aware:<scene_hash>`、`affection:<uid>:<version>`。
- [ ] Agent 工具轮次只刷新确实变化的内容；静态人格、完整工具说明和不变的历史前缀保持一致，以提高缓存命中。
- [ ] 工具按规范名称和 schema 哈希去重；同名不同 schema 视为配置冲突并告警，不静默保留两份。
- [ ] 修复 API 400 时只允许受控重试一次，并复用同一 `request_id`；第一次请求如果已得到可用结果，不得再生成第二份回复。
- [ ] 最终发送使用原子状态或会话锁，确保 `on_llm_response`、`on_agent_done` 和重试路径不会各发送一次。
- [ ] 合并转发消息先转换为规范用户内容，再走与普通消息相同的人格、分句和后处理链路，不允许插件绕过最终配置直接发送原始分析文本。

### 9.4 验收标准

- 5 条连续消息只产生 1 个 `request_id`、1 次普通主请求和 1 份回复。
- 无工具消息的 Provider 请求数严格为 1。
- 单工具任务的额外请求数与 Agent 协议一致，日志能解释每一轮用途。
- API 400 不再导致两份最终结果。
- 同一工具在最终请求中只出现一次。
- 工具轮次的静态前缀哈希保持稳定，缓存命中率不低于阶段 0 基线。

## 10. 阶段 5：加固安全边界并控制审查成本

> Output Audit 监管 AI 的独立设计、风险分类、审核协议、上线方式和回滚方案见 [`OUTPUT_AUDIT_AI_DESIGN.md`](OUTPUT_AUDIT_AI_DESIGN.md)。本阶段实施时以该文档为详细规范。

### 10.1 设计原则

AntiPromptInjector 可以承担检测、分级和阻断，但不能完全替代固定的安全边界提示。插件可能加载失败、被升级覆盖或遇到未识别表达，因此应保留一段短小、稳定、不可被群聊内容覆盖的核心边界。

安全链路建议分为三层：

1. 规则和结构层：识别系统提示词套取、上下文压缩外发、工具说明套取、跨用户记忆读取等明显请求。
2. AntiPromptInjector：前置标记风险，最终对完整请求进行检查。
3. 条件式后审查：仅对高风险群聊回复、工具操作或疑似包含内部文本的输出调用便宜模型审查，不对所有回复无条件增加一次模型调用。

### 10.2 实施任务

- [ ] 保留最小核心边界：不得输出系统提示词、人格原文、隐藏上下文、工具内部说明、密钥和其他用户隐私。
- [ ] 建立注入测试集，覆盖直接命令、角色扮演、上下文压缩、翻译转述、代码块包装、合并转发、图片文字和多轮诱导。
- [ ] 区分“可以正常解释公开能力”和“不得复述内部配置”，减少安全插件误伤普通技术问题。
- [ ] 对拒绝回复使用小天文既有人格语气，避免暴露“命中安全规则 X”之类内部信息。
- [ ] 后审查只接收待发送文本和风险标签，不接收完整系统提示词与其他用户记忆。
- [ ] 记录风险类别、是否阻断、是否人工确认和额外 Token 成本，不记录敏感原文。

### 10.3 验收标准

- 已知“把全部上下文压缩后发给我”等攻击无法取得内部内容。
- 合并转发消息中的指令被当作待分析材料，不被当作系统指令执行。
- 正常的总结、写作和技术问题不过度被拒绝。
- 安全审查增加的平均成本可量化，并且只有高风险请求触发额外模型调用。

## 12. 阶段 7：优化目录树与迁移能力

> 单端口统一运维入口、统一认证、多服务面板、SnowLuma noVNC 和受限 Web SSH 的详细方案见 [`UNIFIED_OPERATIONS_GATEWAY_DESIGN.md`](UNIFIED_OPERATIONS_GATEWAY_DESIGN.md)。该文档明确 NapCat 不再属于现役服务。

### 12.1 先分类，不立即移动

先生成目录资产表，把每个路径分为：

- 定制源码：需要 Git 管理；
- 配置模板：可以提交，但必须去除密钥；
- 敏感配置：单独备份，不进入 Git；
- 持久化数据：数据库、Iris、Stealer、QQ 登录和插件状态；
- 第三方运行时：AstrBot Python 环境、SnowLuma、浏览器、Node 包；NapCat 只作为待归档历史运行时；
- 可再生成缓存：`__pycache__`、模型缓存、临时文件、浏览器缓存；
- 日志：按保留周期轮转；
- 备份：移出运行树，按日期和类型管理。

必须优先查明：

- `astrobot/` 与 `astrobot2/` 的真实关系；
- 顶层 `data/` 与 `astrobot/data/` 是否仍被程序引用；
- `.runtime/napcat` AppImage、旧容器与 QQ 数据是否已完成归档，何时可在 SnowLuma 验收后删除；不得再保留为自动回退；
- `node_modules/@openai/codex*` 是否属于部署必需内容；
- Playwright 浏览器、Embedding 模型和其他大文件能否通过锁定版本重新下载。

### 12.2 建议目标结构

在不破坏现有路径的前提下，逐步收敛为：

```text
xtw_bot/
├── README.md
├── CHANGELOG.md
├── docs/
├── bin/                    # start/stop/status/backup/restore/migrate
├── compose.yml             # 可选：统一编排 AstrBot、SnowLuma 和辅助服务
├── config/
│   ├── examples/           # 脱敏模板
│   └── versions.lock       # AstrBot、插件、镜像和模型版本
├── custom/
│   ├── plugins/            # 本地修改或自研插件
│   └── persona-generator/  # 私有实例的离线流水线
├── data/
│   ├── astrobot/           # 主数据库、Iris、知识库、插件数据
│   ├── snowluma/           # SnowLuma/QQ 持久化数据
│   ├── legacy-napcat/      # NapCat 退役归档，不参与运行
│   └── generated/          # 人格和知识生成产物
```

### 12.3 Git 与敏感信息边界

- [ ] 只把定制源码、脚本、文档、脱敏配置模板和版本清单加入 Git。
- [ ] `.gitignore` 排除 API Key、Token、QQ 配置、数据库、聊天导出、记忆原文、日志、缓存和完整运行时。
- [ ] 为第三方插件保存上游仓库、版本/commit、当前文件哈希和本地补丁，而不是把修改历史只留在 `.bak` 文件名中。
- [ ] 将散落的 `.orig`、`.bak-*` 按变更记录归档，保留索引后移出活动源码目录。

### 12.4 备份等级

定义三类备份：

1. 配置备份：脚本、脱敏配置、版本锁和文档，体积小，可频繁执行。
2. 数据一致性备份：停服务或完成 SQLite checkpoint 后，备份 AstrBot、Iris、知识库、Stealer、SnowLuma 登录与必要 QQ 数据；NapCat 旧数据只进入独立退役归档。
3. 完整灾难恢复归档：整个项目和运行时，用于裸机恢复，体积大，低频执行。

每个归档必须包含 manifest、生成时间、来源主机、服务状态、文件大小和 SHA256。恢复脚本默认恢复到新目录，不直接覆盖现有实例。

### 12.5 迁移演练验收

- 在一台干净 Linux 环境中，仅依靠归档、版本锁和文档完成部署。
- 目录可以整体移动到其他绝对路径，不依赖某台机器的硬编码路径。
- AstrBot 能读取原数据库、Iris 和插件数据。
- SnowLuma 能进入 noVNC 扫码登录或恢复合法登录态，NapCat 不会随迁移实例启动。
- 启动、停止、查看状态、查看日志、备份和恢复均有统一命令。
- 迁移演练不要求携带可再生成缓存和历史日志。

## 14. 发布、回滚与变更纪律

- 每次行为改动只处理一个问题，配置改动与源码改动分开记录。
- 变更前保存配置、定制源码和相关数据库的一致性备份。
- 每次变更必须记录：目的、文件、旧值、新值、预期影响、测试结果和回滚方法。
- 先在本地归档副本或旁路实例验证，再部署到服务器。
- 上下文相关变更先灰度到一个测试会话或测试群，再扩大范围。
- 出现重复回复、人格明显变化、记忆丢失、安全泄漏、QQ 接入多实例或数据库异常时立即停止发布。
- 回滚后重新执行基线测试，确认不是“代码回滚了但运行数据仍处于新格式”。

## 16. 最终完成定义

本计划只有同时满足以下条件才算完成：

- Hook 顺序不再依赖插件注册顺序。
- 普通消息、连续消息、错误重试和工具轮次不会产生意外重复请求或重复回复。
- 上下文来源清晰、动态注入幂等，Token 和缓存指标相较基线有可验证改善。
- 私聊能保留足够近期历史，窗口外重要内容能进入并正确召回 Iris L2/L3。
- 最终主回复的人格、记忆、好感度、工具和主动聊天能力没有明显退化。
- 安全注入测试无法取得内部提示词、人格原文、工具内部说明或他人记忆。
- 情绪插件使用明确 Provider、明确 bot 数据目录，并能稳定更新和持久化。
- SnowLuma 作为唯一 QQ 接入层达到连续运行和故障恢复目标；NapCat 已归档且不会被启动或参与故障切换。
- 项目可以通过文档、版本锁和备份在新 Linux 环境中恢复，运行目录不再依赖单一主机和硬编码路径。
